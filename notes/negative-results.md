# 负结果与待验证假设

记下来免得重复踩坑。

## ISF 指令体

在找到两层解密之前，对"解密后的字节流"试过以下假设，全部失败：

- 整段单字节异或（`0x20` `0x30` `0x55` `0xff`、`SECRETFILTER`、`KIZUNAR`、`SM2MPX10`、文件名派生）
- 简单加减、半字节交换
- rol/ror 1–7 位
- LZSS（12 组参数）
- 长度前缀记录（u32/u16，含对齐变体）
- 计数前缀记录

> 结论：**没有第三层加密**。之前看着像乱码，是因为指令流里大量操作数是二进制数值（`0x44` `0x05` `0xF4` 三种就占 75%），不是加密。

## GGD 图像

- 裸 24bpp / 16bpp：扫 offset 0–63 × stride 96×1..4，相邻像素相关性 = 随机
- 纯 RLE（多种 (计数,值) 组合）：只吃掉文件一小部分
- LZSS 12 组参数：失败
- 记录形状穷举 `[u8 a][u8 b][u8 n][k·n 字节]`（k=1..4，起始 4–24）：无一种能恰好吃到文件末尾
- 整段异或：不同文件前 20 字节高度相似，排除加密

## GGD 压缩流：这一轮试过但失败的路线

token 框架现在已经验证了大半（见 `docs/02-formats.md` 第 3.1 节），下面这些是**试过不行的**：

- 用"重复/复制/字面"三件套硬解全图：`CG2_BAO` 第 0 行第 22 像素必失步，30 张对照图 **0 张**能整行对上
- `00 <n> <x>` 的计数取 `n`、`n+1`、`2n-1`、`n+(x&1)`、`n+((x>>2)&1)` 等变体：没有一个能同时满足
  `MODORU` 的 `00 02 0a`→2 个、`CG2_BAO` 的 `00 02 05`→3 个
- 把 `00` 的第三字节当调色板索引 / 颜色哈希 / 绝对下标：`b=5` 同时对应两种不同颜色，排除
- 把 `01/02/03` 的距离放在第 2 字节或第 3 字节的两种排法：只能各对一半，`01` 必须用第 3 字节、`03` 必须用第 2 字节
- 短形式按 1 字节 vs 2 字节：两种都试过，各自都有反例
- 用 DFS/参数扫描（`00` 计数 × 颜色来源 × `01/02` 计数 × 距离下标 × 短形式阈值，共 720 组）：
  最好的一组只解出 1 行

### 在 `KIZUNAR.EXE` 里找解码器（已排除的定位手段）

- 搜魔数立即数 `b9 aa b3 b3` / `b3 b3 aa b9`：0 命中 → **解码器根本不校验魔数**（靠归档里的类型表）
- 搜 `0f b7 ?? 04`（读 `word[+4]`）、`0f b7 46 04`、`66 8b 40 04`：全部 0 命中
- 搜 `6b c? 03`（imul ×3）：0 命中；`8d 04 40`（lea ×3）16 处，逐个看都不是解码器
- 搜 `83 c6 03` / `83 c7 03`（指针 +3）：命中 `0x410ed0`（截图存盘，32bpp→24bpp 转换）、`0x458880`（memmove）
- 搜 `3c 01/02/03`（cmp al,1/2/3 的 switch）：只剩 5 个函数，逐个看都不是
- 归档工厂 `FUN_0043d2e0` case 1 → 对象 0x1858 字节、vtable `0x473c20` 只有 3 个槽
  （析构 `0x43d820`、通用文件打开 `0x430ae0`、`0x43d800` 不是函数）→ **解码不在虚函数里**
- `0x473c38` 指向的"描述符"实际是消息映射，里面两个函数 `0x441290`/`0x4415a0` 是 IME/窗口处理

> 结论：**解码器是静态内联/非虚函数，靠字符串和魔数都定位不到**。继续在 EXE 里盲搜性价比已经很低。


## GGD 压缩流：最终结论（推翻上面所有假设）

上面那一整轮失败的原因是**两个操作码的形态判断错了**，不是缺一条规则：

- `02` 不是 3 字节 `02 <k> <d8>`，而是 **4 字节 `02 <k> <d16>`**（16 位距离）
- `04` 不是「原始段 0 像素」的填充，而是 **3 字节 `04 <d16>` = 复制 1 像素**
- 根本**没有**「上一个距离 / lastd」机制，也**没有**每行控制字节、没有分块头
- `05`–`FF` 全部是「原始段，长度 = b-4」，不是 `>=0x20` 单像素

直接证据：`FUN_0040b190` 的反编译（见 `docs/02-formats.md` 3.1）。
补丁图「每 251 像素一个填充字节」的真身是「每 251 像素一个 `0xFF` 原始段头」。

**为什么之前一直解不出行首**：640 宽的图第 1 行第 0 像素要引用第 0 行，距离 640 > 255，
8 位距离根本表达不了，于是编码器用 `02`（16 位距离）。之前把 `02` 当 3 字节，
从第 1 行开始整个流就错位了。

### 定位解码器的有效手段（记录一下，以后能复用）

按魔数、按 `word[+4]`、按 `cmp al,3`、按 `lea *3`、按虚函数表**全部无效**。
真正管用的是**按 token 的语义形状搜**：

- 重复 token 会读「输出指针往回 3 字节」，于是搜 `[reg - 3]` 的内存操作数
- 命中 `0x40b20c: mov al,[esi-3]; mov cl,[esi-2]; mov dl,[esi-1]` → 函数 `FUN_0040b190`
- 再看它的分派 `0x40b1e2: cmp eax,4; ja ...; jmp [eax*4+0x40b398]` 就全清楚了

教训：**先找数据形状（`[reg-3]` 这种），别找常量**。常量（魔数、`4`、`3`）在 MFC 里到处都是。
