# ISF 虚拟机

> 结论先行：解释器是 `FUN_00434ec0`（`0x434ec0`）。**163 个合法 opcode 全部有确定的处理函数地址**，
> 高频的 6 个（覆盖 95%）语义已经确认。这份文档是把「93 种 opcode 只认识 7 种」推进到
> 「每个 opcode 都知道该去读哪个函数」的存档。

---

## 1. 解释器长什么样

`FUN_00434ec0(vm, unused)` 一次只执行**一条**指令，返回 0 表示「跳转了」、1 表示「顺序执行」。
主循环在外面反复调用它。函数开头的取指部分：

```c
pb = vm->code;            // +0x18  当前指令指针
vm->instr = pb;           // +0x1C  本条指令起始地址
vm->op    = *pb;          // 操作码
vm->code  = pb + 1;
len = pb[1];
vm->code  = pb + 2;
if (len & 0x80) {         // 长格式
    len = ((len << 8) | pb[2]) & 0x7fff;   // 大端 16 位，清掉 bit15
    vm->code = pb + 3;
}
```

这就是 `docs/02-formats.md` 里那条 `len == 0x80 / 0x81` 规则的**出处**：

- `0x80 NN` → `(0x8000|NN) & 0x7fff` = `NN`
- `0x81 NN` → `(0x8100|NN) & 0x7fff` = `0x100 + NN`

然后按 `op` 查表分派：

```
op > 0xFF          -> 非法
case = DAT_004359e4[op]      // 256 字节映射表，0xA3 = 非法
jmp  [0x435754 + case*4]     // 164 项跳转表
```

每个 case 都是几字节的薄壳，做的是「`mov ecx, esi` / `push len` / `call 0x43xxxx`」。
所以 **opcode → 处理函数** 是一一对应的（只有 `0x33`/`0x3B` 共用，`0x64`/`0x66`/`0x67`/`0x68`/
`0xBE`/`0xBF`/`0xE9` 共用）。完整对照表见第 6 节。

## 2. VM 的状态

| 偏移 | 内容 |
|---|---|
| `+0x00` | 错误标志（1 = 已中止）|
| `+0x10` | **标签表**：`u32*`，来自 ISF 头部的偏移表 |
| `+0x14` | **代码基址**（`plain + head_len`）|
| `+0x18` | **当前指令指针** |
| `+0x1C` | 本条指令起始地址 |
| `+0x20` | 指令结束哨兵，`FUN_00434eb0` 把它置 `-1` |
| `+0x48` | **返回地址栈**（存「下一条指令 − 代码基址」的 u32）|
| `+0x4C` | 返回栈深度（u16，上限 `0x3FF`，溢出就报错中止）|
| `+0x550` | **变量槽**：`{u32* data, int count}`，`FUN_00424a60` 写、`FUN_00424b20` 读 |

三个原语（`FUN_00434960/80/90`）：

| 函数 | 作用 |
|---|---|
| `FUN_00434960` | 读 1 字节，指针 +1 |
| `FUN_00434980` | 读 2 字节，指针 +2 |
| `FUN_00434990` | 读 4 字节，指针 +4，并顺手 `FUN_00424b20` 解引用 |

`FUN_00435af0(vm, idx)` = `vm->code = vm->labels[idx]`，即**跳转到标签**。

## 3. 操作数编码（很重要）

所有 32 位操作数都走 `FUN_00424b20` 解码，一个 word 里塞了三件事：

| 位 | 含义 |
|---|---|
| `31` | **间接**：`v = vars[v]` |
| `30` | **随机**：`v = rand() % v` |
| `29` | **符号**：把 30 位值符号扩展到 32 位 |
| `0–28` | 值 |

```c
v = raw & 0x3fffffff;
if (raw & 0x20000000) v |= 0xc0000000;   // 变成负数
if (raw & 0x80000000) v = (0 <= v < count) ? vars[v] : 0;
if ((raw & 0x40000000) && v) v = rand() % v;
```

所以 `0x80000061` 不是「二十一亿」，而是「变量 0x61 的值」。看脚本时先看最高位。

## 4. 表达式：`0x44` 赋值（占全部指令 27%）

`0x44` 的载荷是 `[目标槽 u16]` + 若干 `[运算符 u8][操作数 u32]`，遇到第一个 `> 4` 的字节结束。

```
op 0 = +   1 = -   2 = *   3 = /   4 = %
```

求值是「两个累加器」的无括号链式求值（`FUN_00438790`）：`iVar4` 累计加减项，
`iVar5` 暂存乘除项，遇到下一个加减就把 `iVar5` 并进 `iVar4`。也就是说**乘除优先**，但没有括号。

实例（`SNR00.ISF` 第 14 条）：

```
44  61 00 | 00 | 62 00 00 80 | 05
    ^目标   ^+   ^变量0x62     ^结束
等价于：vars[0x61] = vars[0x62]
```

另一个：`44 61 00 | 00 | 61 00 00 80 | 01 | 14 00 00 00 | 05` → `vars[0x61] = vars[0x61] - 20`。

## 5. 控制流：`0x05` / `0x06` / `0x07` / `0x47`

### `0x05` CALL 标签（占 25%）

```c
label = read_u16();
if (ret_depth > 0x3FF) abort();
ret_stack[ret_depth++] = next_instr - code_base;
vm->code = labels[label];
```

### `0x06` RET

```c
if (ret_depth == 0) abort();
vm->code = code_base + ret_stack[--ret_depth];
```

### `0x07` SWITCH

```c
v     = read_u32();     // 选择子（通常是变量）
n     = read_u8();
if (0 <= v < n) {
    label = read_u16_at(code + v*2);
    jump(labels[label]);
}
```

载荷长这样（`SNR00.ISF` 第 351 条）：

```
07  61 00 00 80 | 14 | 35 0b 36 0b 37 0b 38 0b ...
    ^var 0x61      ^20  ^标签 0b35, 0b36, 0b37, 0b38 ...
```

——变量 0x61 的 20 个分支，标签还是连号的，非常典型。

### `0x47` 比较 / 条件（占 0.36%）

```c
a   = read_u32();
cmp = read_u8();
b   = read_u32();
if (test(a, cmp, b)) {
    act = read_u8();
    if (act == 0)   jump(labels[read_u16()]);
    if (act == 1)   vars[read_u16()] = read_u32();
    if (act == 0xFF) /* 什么都不做，结束 */;
}
```

| cmp | 含义 |
|---|---|
| 0 | `a == b` |
| 1 | `a <  b` |
| 2 | `a <= b` |
| 3 | `a >  b` |
| 4 | `a >= b` |
| 5 | `a != b` |

实例：`47 61 00 00 80 | 04 | b8 0b 00 00 | 00 | 1f 00 | ff`
→ `if (vars[0x61] >= 3000) goto label 0x1F`。

## 6. 已确认语义的指令

| opcode | 名称 | 载荷 | 语义 |
|---|---|---|---|
| `00` | NOP | — | 空指令（34 次）|

| `FB` | TMRST | — | 计时器清零（`FUN_004345c0`：`vm+0x184 = 0`）|

`F4` / `F5` 的载荷**只有 `00` 和 `01`**，在 `SNR00.ISF` 里各出现 3225 / 3141 次
（3141 正好等于该文件的台词条数），高度怀疑是「文本窗口 / 语音播放」这类 UI 开关，
但具体含义还没从使用侧反推出来。

## 9. 每条台词的标准形状

把执行轨迹和静态指令对起来看，带语音的台词长这样：

```
F4 01                        ; SET_FLAG 1
44 5A 00 | 00 | <n> | 05     ; vars[0x5A] = n          <- 语音编号
F0 04 "VOICE2"               ; 语音归档
78 "ONK0001"                 ; 语音文件名
05 EA 0C                     ; CALL label 0x0CEA       <- 显示子程序
2B 00 03 04 36 FF <cp932>    ; 台词，说话人槽 0x36
```

这条 `05 EA 0C` 解释了为什么 `0x05` 占了全部指令的 25%：**每句台词都要调一次显示子程序**。
显示子程序里就是那些高频的中频 opcode（`0x79` `0x81` `0x85` `0x86` `0x87` `0x49` `0x31`），
它们一次文本执行一次，所以执行次数全都卡在 3130 上下。

其中 `0x85` / `0x86` / `0x87` / `0xFB` / `0xFC` 的语义已经确认（见 §10），`0x87` 干脆是空指令。
剩下 `0x79` / `0x81` / `0x49` / `0x37` 还是「文本框排版」那一层，属于**重写时自己实现**的部分——
原引擎怎么画的并不需要照抄。

## 10. 输入 / 计时器 / 菜单循环

### 10.1 `0x85`：轮询输入

```
85 <u16 var_a> <u16 var_b> <u8 mode> <u8 flags>
```

处理函数 `FUN_0043b800`：

```c
if (flags & 2) { FUN_004407a0(engine, var_a, var_b, mode, flags & 1); return; }   // 只看悬停
FUN_00440b40(engine, var_a, var_b, mode, flags & 1, flags & 4);                  // 完整轮询
```

`FUN_00440b40` 干的事（这是整个输入系统的核心）：

```c
GetCursorPos(&pt); ScreenToClient(hwnd, &pt);
hit = FUN_00440910(this, pt.x, pt.y);          // 命中哪个 UI 热区
FUN_00424a60(vars, var_a, hit);                // vars[var_a] = 热区号
...
ev = 0;
if (GetAsyncKeyState(0x0D) & 0x8000) ev = 2;   // Enter
if (GetAsyncKeyState(0x1B) & 0x8000) ev = -1;  // Esc
if (GetAsyncKeyState(0x02) & 0x8000) ev = -1;  // 鼠标右键
FUN_00424a60(vars, var_b, ev);                 // vars[var_b] = 事件
```

| 变量 | 取值 |
|---|---|
| `vars[var_a]`（热区）| 热区序号；`-1` = 没指到任何东西；`-2` = 鼠标在 640×480 画面外 |
| `vars[var_b]`（事件）| `0` = 什么都没发生；`2` = 确定（Enter / 左键 / 手柄 A）；`-1` = 取消（Esc / 右键 / 手柄 B）|

### 10.2 `0xFB` / `0xFC`：毫秒计时器

| opcode | 载荷 | 处理函数 | 语义 |
|---|---|---|---|
| `FB` | — | `FUN_004345c0` | `vm+0x184 = 0`，计时器清零 |
| `FC` | `u16 var` | `FUN_0043dcb0` | `vars[var] = FUN_004345d0()` |

`FUN_004345d0` 就是「`timeGetTime()` 累计差值」：第一次调用记下时间戳，之后每次把
「现在 - 上次」累加进 `vm+0x188` 并返回。所以 `FC` 读的是**从上次 `FB` 到现在的毫秒数**。

### 10.3 两个标准形状

**等待 N 毫秒**（`START.ISF` 0xEA2，`STAFF.ISF` 0x80BF 都是这个形状）：

```
FB                           ; 计时器清零
L: FC 0A                     ; vars[0x0A] = 已过毫秒
   47 0A 00 00 80 | 04 | 0C 00 00 80 | 00 | 0F 00 | FF
                             ; if vars[0x0A] >= vars[0x0C] goto L_exit
   04 0E 00                 ; goto L
L_exit:
```

**菜单循环**（`TITLE.ISF` 0x7B9）：

```
L: 85 07 00 08 00 05 01      ; vars[7] = 热区, vars[8] = 事件
   47 09 00 00 80 | 00 | 07 00 00 80 | 00 | 0A 00 | FF
                             ; if vars[9] == vars[7] goto 跳过悬停处理
   08 ...                   ; 悬停变化 -> call 对应子程序（放音效之类）
   44 09 00 | 00 | 07 00 00 80 | 05        ; vars[9] = vars[7]
   47 08 00 00 80 | 03 | 01 00 00 00 | 00 | 0B 00 | FF
                             ; if vars[8] > 1 goto 派发
   04 09 00                 ; goto L
派发: 07 07 00 00 80 ...      ; switch vars[7] 分派到各个按钮
```

### 10.4 对移植的含义

虚拟机需要**两个宿主回调**，不能自己造：

```rust
fn poll_input(&mut self, mode: u8, flags: u8) -> (i32, i32);  // 0x85
fn now_ms(&mut self) -> i32;                                 // 0xFC
```

Python 版默认返回 `(-1, 0)`（没人操作）和「每次轮询 +16 ms」（60fps 一帧）。所以：

- 剧情脚本照样跑得完（它们等的是计时器，不是输入）；
- `TITLE` / `BGMMODE` / `CGMODE` / `SEXMODE` 会一直空转 —— **这不是 bug，是它们本来就在等玩家点**。

## 11. 加载器 `FUN_00434b50`（顺便把文件头钉死了）

`0x02 CMDNAME`（`FUN_004363e0`）会先把「模块名 → 当前偏移」记进 `vm+0x4F`（步长 13）
和 `vm+0x12C`（u32 数组），然后调用加载器 `FUN_00434b50(vm, name)`：

```c
iVar6 = FUN_00430e00(vm->archive, name, 0);   // 找成员
size  = FUN_004310b0(vm->archive);
buf   = GlobalAlloc(0x40, size + 4);
FUN_00431070(vm->archive, buf, size);         // 读出来
FUN_00444f60(name, buf, size);                // 解密
magic = swap16(*(u16*)(buf + 4));             // 41 个文件全是 0x9597
```

| magic | 变换 | 有标签表 |
|---|---|---|
| `0x9597` | 每个字节循环左移 6 位 | 是 |
| `0x89CE` | 每个字节 XOR `buf[6]` | 是 |
| `0x97D1` | 每个字节取反 | 是 |
| `0x8DF7` | 不变（但置错误标志）| — |
| 其它 | 不变 | 否 |

有标签表时：

```c
n = (*(u32*)buf - 8) / 4;                     // 文件头 8 字节
label[i] = buf + *(u32*)(buf + 8 + i*4);      // 相对偏移 -> 绝对指针
memmove(buf, buf + 8 + n*4, size - 8 - n*4);  // 把代码往前挪，盖掉文件头
vm->code_base = buf;
```

这就是 `head_len = 8 + 4n` 的出处，也解释了为什么标签值全都是**相对代码基址**的偏移。

## 12. 画面：槽 + 模块（还没完全解开，但骨架清楚了）

### 12.1 绘制槽

`0x84` 定义「槽」——引擎里是一张 64 项的固定表，每项 0x1C 字节，起始于 `engine+0xE0`：

```text
0xE0  u32   x        0xE4  u32   y        0xE8  u32   w        0xEC  u32   h
0xF0  u8    层/模式   0xF2  u16   图像号   0xF4  u8  ?   0xF5  u8  ?   0xF6  u8  ?
0xF8  u8    鼠标命中标记（FUN_004407a0 每帧清）
```

每个剧情脚本的第一条指令都是 `84 19 ...`（长度 25），把槽 0 设成 640×480 全屏：

```
033e8  84 25  00 | 00 00 00 00 | 00 00 00 00 | 80 02 00 00 | e0 01 00 00 | 00 | ...
              slot    x=0          y=0          w=640        h=480
```

`0x57` 再对槽下绘制命令。`SNR00` 里 421 条 `0x57` 全是同一个形状：

```
57 35  13 | 01 00 00 00 | 00 00 00 00 | 00 00 00 00 | 80 02 00 00 | e0 01 00 00 | e8 03 00 00 | 0 | 0
       cmd  slot=1        x=0          y=0          w=640        h=480        dur=1000ms
```

`cmd` 的分布是 `0x13`(19) / `0x18`(24) / `0x19`(25) / `0x1C`(28) / `0x1D`(29) / `0x0F`(15) / `0x10`(16) /
`0x00` / `0x01`，配上 600 / 1000 / 1500 / 2000 ms 的时长——**这是淡入淡出**。

### 12.2 模块系统

`CGLIB.ISF` 里有 **1017 条 `0x56`（图像注册）**，`BG01AC` / `BG02AA` / … 全部背景名都在里面；
而剧情脚本自己只有 7 条（都是本场景专用的 `EFEC0x` 特效）。

也就是说：**剧情脚本本身不画背景，它调 CGLIB**。这套调用机制已经在第 13 节完全解开了。

### 12.3 移植时怎么办

好消息是：**这一层不需要照抄**。重写版可以自己定义场景模型——
只要能从脚本里读出「现在该显示哪张图、在什么位置」，剩下的交给自己的渲染器。
而「该显示哪张图」这件事，`0x56` 的字符串已经全在脚本里了（CGLIB 1017 条）。
## 13. 模块系统：`0x01` / `0x02` / `0x03`（已跑通）

上一版写「这套切换的具体时机还没验证」。现在全部钉死了，下面是完整结论。

### 13.1 三条指令的分工

| op | 名字 | 引擎函数 | 语义 |
|----|------|----------|------|
| `0x01` | JUMPSCRIPT | `FUN_004363a0` | 跳剧本：清空模块栈/返回栈，载入新剧本，PC=0，**不返回** |
| `0x02` | CALLMOD | `FUN_004363e0` | 调模块：压返回地址（= 本指令末尾），载入新剧本，PC=0 |
| `0x03` | END | `FUN_00436460` | 模块返回：弹栈、重载调用者、PC=返回地址；栈空 = 脚本结束 |

`0x02` 的格式是 `02 <名字\0>`，名字**内联在指令流里**，最长 13 字节
（`FUN_004349b0` 逐字节读，遇 0 停）。它没有偏移操作数：
返回地址直接用取指时存下的长度算——派发桩里的 `add edx, ecx`，
`edx` 其实是 `len`（`ebx`），`ecx` 是 `vm+0x1C`（本指令起始地址）。

### 13.2 两套栈，别搞混

```text
模块栈（0x01/0x02/0x03 用）
  vm+0x4E          u8    模块深度
  vm+0x4F + d*13   名字   第 d 层的模块名（9 字节定长）
  vm+0x12C + d*4    u32   第 d 层的返回偏移（相对 code_base）

调用栈（0x05/0x06 用）
  vm+0x4C          u16   深度（上限 0x400）
  vm+0x48          数组   返回偏移
```

`0x05 CALL <标签号>` 压「本指令末尾」，`0x06 RET` 弹出来跳回去。
`0x08 CSWITCH` 命中分支时也会压一个（这就是它和 `0x07` 的唯一区别）。

`0x01` 先调 `FUN_00435b00`，把 `+0x4E / +0x4C / +0x44` 全清零——所以它是干净的场景切换。

### 13.3 所谓 state 其实是 opcode

`FUN_00434ec0` 开头的 `vm+0x20` 不是状态机，而是**当前指令的 opcode**：

```c
434ecd  cmp [esi+0x20], -1     ; -1 = 需要取指
434ed1  jne 0x43518f           ; 否则直接派发（0x02 载入后 PC 已由加载器设好）
434ee9  eax = vm->pc
434eee  vm->insn = eax         ; +0x1C = 本指令起始地址，标签运算的基准
434ef4  vm->op = *pc++
```

派发完的公共尾巴在 `0x435176`：

```c
if (handler_ret == 0) return 1;   // 处理函数自己改了 PC
if (vm->b_0c != 0) return 1;      // 刚载入模块，别再前进
vm->pc = vm->insn + len;          // 正常前进
```

### 13.4 `0x3A SYSIF` 的 16 个系统号

跳转表在 `0x438658`，`sid > 0x0F` 一律不跳。每个分支都是「拿一个全局/引擎字段和操作数比」：

| sid | 比较对象 | 语义 |
|-----|----------|------|
| 0 | `[0x4891ae]` | 等于 arg |
| 1 | `[0x4891d4]` / `[0x4891b8]` | 鼠标边沿：arg 0/1/2 三种组合 |
| 2..7 | `[0x4891c8/d8/dc/e0/cc/d0]` | 等于 `(arg == 0)` |
| 8 | `FUN_00435c40(vm,0)` | 输入锁住返回 1，否则返回 `vm+0x549` |
| 0x0A | 常量 | `arg != 0` |
| 0x0B | `[0x4891a1]` | 与 `(arg != 0)` 同真同假 |
| 0x0C | `vm+0x54A` | 「跳过模式」：`(b54a == 1) == (arg == 0)` |
| 0x0D | `FUN_0043f970` | 文字管理器：1=还在打字 2=打完待确认 0=空闲 |
| 0x0E | `FUN_00435d50` | 输入状态字节 `vm+0x54D`，按住键时或上 2 |
| 0x0F | `engine+0x801` | 与 `(arg != 0)` 同真同假 |

`0x0D` 是**打字机效果的等待**：`SYSIF 0D 00 -> 自己` 就是「字打完之前原地转」。
无人值守时必须按「瞬间打完」返回 0，否则死循环。

同理 `0x0E` 不能乱猜：它是「输入状态 == arg」，没人操作时是 0，不是 3。
早期为了跑通把它硬编码成 3，结果把分支带歪、返回栈错位。

### 13.5 剧本链

`0x01` 串起来的主线（`kzn dump` 实测）：

```text
SNR00 → SNR01 → … → SNR11 → SNRC1 → SNRC2 → STAFF → SNRC3 → TITLE → SNR00 …
```

一圈约 36,000 条台词、270 万条指令。也就是说**整部游戏是一条链**，
走到 `TITLE` 再开新游戏才回到 `SNR00`。导出剧本时要「回到走过的剧本就停」，
否则会无限套圈。

### 13.6 实测结果

- `tools/isf_vm.py` 与 `rust/` 两边跑 41 个脚本 × 20 万步，事件流**逐字节相同**（41/41）。
- `SNR00` 一条链 300 万步内产出 7,052 条 `0x56` 图像事件，名字是真的
  （`BG01AC.GG0`、`EV001.GG0`、`TRA01.GG2`…）——背景终于出来了。

### 13.7 下一步：把槽和绘制接上

现在事件流里已经有「注册了哪张图」，缺的是「这张图此刻在哪个槽、什么位置」。
那条链是 `0x56`（注册）→ `0x84`（槽绑定）→ `0x57`（绘制/淡入淡出），
把这三个拼起来就能在任意一条台词处截一张真实画面。

## 14. 画面还原：槽 0 就是当前背景

### 14.1 三个 op 连起来

| op | 作用 | 实测数量（CGLIB / SNR00 链） |
|----|------|------------------------------|
| `0x56` | 把编号注册成图像名 | 1017 / 7052 |
| `0x84` | 定义槽：矩形、层、绑定图像号 | 0 / 21 |
| `0x57` | 绘制 / 淡入淡出 | 122 / 22893 |

`0x84` 的完整格式（`FUN_0043b6f0`，写 `engine+0xE0+slot*0x1C`）：

```text
84 <u8 slot> <u32 x> <u32 y> <u32 w> <u32 h> <u8 layer> <u16 img> <u8 f6> <u8 f5> <u8 f4>
```

`0x57` 是 `57 <u8 cmd> <u32 img> <u32 x> <u32 y> <u32 w> <u32 h> <u32 dur> <u32> <u32>`（33 字节载荷），
`cmd` 走 `0x439b7c` 的 29 项跳转表，部分分支再读一个 u32。

### 14.2 没有独立的人物层

剧情脚本里所有 `0x57` 的矩形都是 **640×480 全屏**，`cmd` 只出现
`0x00/0x01`（画）和 `0x0F/0x10/0x13/0x14/0x18/0x19/0x1D`（淡入淡出）。
也就是说人物不是单独一层——**人物已经合成进全屏图里了**
（`THA02.GG2` / `TCB02.GG2` / `TMA09.GG2` 这些就是带人物的整屏图）。

### 14.3 当前背景 = 槽 0 的图像

槽 0 永远是 `(0,0,640,480)`，`img` 字段恒为 2；
引擎每次换背景就是把**注册号 2 重新指到新名字**。
所以在每条 `0x2B`（台词）处记下「槽 0 的图像号 → 当前注册名」，
就得到这句台词该配哪张背景。

### 14.4 alpha 的坑（踩过）

`GG0/GG2` 头部 `byte@0x0F bit0` = 有没有独立 alpha 平面：

- **有**（`BAD1.GG2` 之类人物图）：第 4 字节是真 alpha，0..255，avg 10~30
- **没有**（全部 `BG*.GG0` 背景）：第 4 字节恒为 0，**必须当不透明**

不区分的话整张背景会被 `a == 0` 判成全透明，画出来只剩一个文本框。
`Image.alpha` 就是记这个的。

### 14.5 成品

```text
kzn shot <游戏目录> SNR00.ISF <输出目录> --at 300 --lines 301
```

跑 200 万条指令 → 定位第 300 句台词 → 取当时的槽 0 背景 → 解码 → 贴文本框 → 排字 → 出 PNG。
样张 `000.png` / `300.png` / `3000.png` / `8000.png` 背景各不相同，
对应 `BG01AC` / `BG02AC` / `BG17A1` / `BG17C3`。
