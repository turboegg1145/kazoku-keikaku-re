# ISF 虚拟机

> 结论先行：解释器是 `FUN_00434ec0`（`0x434ec0`）。**163 个合法 opcode 全部有确定的处理函数地址**，
> 高频的 6 个（覆盖 95%）语义已经确认。这份文档是把「93 种 opcode 只认识 7 种」推进到
> 「每个 opcode 都知道该去读哪个函数」的存档。

---

## 1. 解释器长什么样

`FUN_00434ec0(vm, unused)` 一次只执行**一条**指令，返回 0 表示「跳转了」、1 表示「顺序执行」。
主循环在外面反复调用它。函数开头的取指部分：

```c
pb = vm->code;            // +0x18  当前指令指针
vm->instr = pb;           // +0x1C  本条指令起始地址
vm->op    = *pb;          // 操作码
vm->code  = pb + 1;
len = pb[1];
vm->code  = pb + 2;
if (len & 0x80) {         // 长格式
    len = ((len << 8) | pb[2]) & 0x7fff;   // 大端 16 位，清掉 bit15
    vm->code = pb + 3;
}
```

这就是 `docs/02-formats.md` 里那条 `len == 0x80 / 0x81` 规则的**出处**：

- `0x80 NN` → `(0x8000|NN) & 0x7fff` = `NN`
- `0x81 NN` → `(0x8100|NN) & 0x7fff` = `0x100 + NN`

然后按 `op` 查表分派：

```
op > 0xFF          -> 非法
case = DAT_004359e4[op]      // 256 字节映射表，0xA3 = 非法
jmp  [0x435754 + case*4]     // 164 项跳转表
```

每个 case 都是几字节的薄壳，做的是「`mov ecx, esi` / `push len` / `call 0x43xxxx`」。
所以 **opcode → 处理函数** 是一一对应的（只有 `0x33`/`0x3B` 共用，`0x64`/`0x66`/`0x67`/`0x68`/
`0xBE`/`0xBF`/`0xE9` 共用）。完整对照表见第 6 节。

## 2. VM 的状态

| 偏移 | 内容 |
|---|---|
| `+0x00` | 错误标志（1 = 已中止）|
| `+0x10` | **标签表**：`u32*`，来自 ISF 头部的偏移表 |
| `+0x14` | **代码基址**（`plain + head_len`）|
| `+0x18` | **当前指令指针** |
| `+0x1C` | 本条指令起始地址 |
| `+0x20` | 指令结束哨兵，`FUN_00434eb0` 把它置 `-1` |
| `+0x48` | **返回地址栈**（存「下一条指令 − 代码基址」的 u32）|
| `+0x4C` | 返回栈深度（u16，上限 `0x3FF`，溢出就报错中止）|
| `+0x550` | **变量槽**：`{u32* data, int count}`，`FUN_00424a60` 写、`FUN_00424b20` 读 |

三个原语（`FUN_00434960/80/90`）：

| 函数 | 作用 |
|---|---|
| `FUN_00434960` | 读 1 字节，指针 +1 |
| `FUN_00434980` | 读 2 字节，指针 +2 |
| `FUN_00434990` | 读 4 字节，指针 +4，并顺手 `FUN_00424b20` 解引用 |

`FUN_00435af0(vm, idx)` = `vm->code = vm->labels[idx]`，即**跳转到标签**。

## 3. 操作数编码（很重要）

所有 32 位操作数都走 `FUN_00424b20` 解码，一个 word 里塞了三件事：

| 位 | 含义 |
|---|---|
| `31` | **间接**：`v = vars[v]` |
| `30` | **随机**：`v = rand() % v` |
| `29` | **符号**：把 30 位值符号扩展到 32 位 |
| `0–28` | 值 |

```c
v = raw & 0x3fffffff;
if (raw & 0x20000000) v |= 0xc0000000;   // 变成负数
if (raw & 0x80000000) v = (0 <= v < count) ? vars[v] : 0;
if ((raw & 0x40000000) && v) v = rand() % v;
```

所以 `0x80000061` 不是「二十一亿」，而是「变量 0x61 的值」。看脚本时先看最高位。

## 4. 表达式：`0x44` 赋值（占全部指令 27%）

`0x44` 的载荷是 `[目标槽 u16]` + 若干 `[运算符 u8][操作数 u32]`，遇到第一个 `> 4` 的字节结束。

```
op 0 = +   1 = -   2 = *   3 = /   4 = %
```

求值是「两个累加器」的无括号链式求值（`FUN_00438790`）：`iVar4` 累计加减项，
`iVar5` 暂存乘除项，遇到下一个加减就把 `iVar5` 并进 `iVar4`。也就是说**乘除优先**，但没有括号。

实例（`SNR00.ISF` 第 14 条）：

```
44  61 00 | 00 | 62 00 00 80 | 05
    ^目标   ^+   ^变量0x62     ^结束
等价于：vars[0x61] = vars[0x62]
```

另一个：`44 61 00 | 00 | 61 00 00 80 | 01 | 14 00 00 00 | 05` → `vars[0x61] = vars[0x61] - 20`。

## 5. 控制流：`0x05` / `0x06` / `0x07` / `0x47`

### `0x05` CALL 标签（占 25%）

```c
label = read_u16();
if (ret_depth > 0x3FF) abort();
ret_stack[ret_depth++] = next_instr - code_base;
vm->code = labels[label];
```

### `0x06` RET

```c
if (ret_depth == 0) abort();
vm->code = code_base + ret_stack[--ret_depth];
```

### `0x07` SWITCH

```c
v     = read_u32();     // 选择子（通常是变量）
n     = read_u8();
if (0 <= v < n) {
    label = read_u16_at(code + v*2);
    jump(labels[label]);
}
```

载荷长这样（`SNR00.ISF` 第 351 条）：

```
07  61 00 00 80 | 14 | 35 0b 36 0b 37 0b 38 0b ...
    ^var 0x61      ^20  ^标签 0b35, 0b36, 0b37, 0b38 ...
```

——变量 0x61 的 20 个分支，标签还是连号的，非常典型。

### `0x47` 比较 / 条件（占 0.36%）

```c
a   = read_u32();
cmp = read_u8();
b   = read_u32();
if (test(a, cmp, b)) {
    act = read_u8();
    if (act == 0)   jump(labels[read_u16()]);
    if (act == 1)   vars[read_u16()] = read_u32();
    if (act == 0xFF) /* 什么都不做，结束 */;
}
```

| cmp | 含义 |
|---|---|
| 0 | `a == b` |
| 1 | `a <  b` |
| 2 | `a <= b` |
| 3 | `a >  b` |
| 4 | `a >= b` |
| 5 | `a != b` |

实例：`47 61 00 00 80 | 04 | b8 0b 00 00 | 00 | 1f 00 | ff`
→ `if (vars[0x61] >= 3000) goto label 0x1F`。

## 8. 跑通验证（`tools/isf_vm.py`）

只实现第 6 节那几条指令，其余按长度跳过，就能**把 41 个 ISF 全部执行到自然结束**。

```
python3 tools/isf_vm.py KIZUNAR.EXE ISF SNR00.ISF --trace          # 逐条指令
python3 tools/isf_vm.py KIZUNAR.EXE ISF SNR00.ISF --out snr00.txt  # 导出带语音名的台词
```

| 指标 | 结果 |
|---|---|
| 41 个文件全部终止于 | `return stack underflow`（= 顶层 `RET`，正常结束）|
| 总步数 | 4,831,643 |
| 执行到的台词 | 60,917 条（静态共 62,405 条）|
| 台词顺序与线性扫描一致 | **34 / 41 个文件逐条相同** |

**34/41 逐条相同**是最强的正确性证据：虚拟机走出来的台词序列，和「按文件顺序把所有 `0x2B`
扫一遍」得到的序列完全一样（只少了文件开头那句 `　ロードに失敗しました。`——它在错误分支里，
正常路径不执行）。

另外 7 个文件在中途分叉，看内容就知道是**真的分支**，不是跑飞：

| 文件 | 分叉点 | 线性扫描 | 虚拟机 |
|---|---|---|---|
| SNR07 | 第 826 条 | 「わーんっ」 | 「わおーーーん」 |
| SNR10 | 第 503 条 | 「……涼むか」 | 「おいっす！」 |

虚拟机里所有变量初值都是 0，所以它走的是「默认分支」；真机上变量由存档/旗标填，就会走别的分支。

## 9. 每条台词的标准形状

把执行轨迹和静态指令对起来看，带语音的台词长这样：

```
F4 01                        ; SET_FLAG 1
44 5A 00 | 00 | <n> | 05     ; vars[0x5A] = n          <- 语音编号
F0 04 "VOICE2"               ; 语音归档
78 "ONK0001"                 ; 语音文件名
05 EA 0C                     ; CALL label 0x0CEA       <- 显示子程序
2B 00 03 04 36 FF <cp932>    ; 台词，说话人槽 0x36
```

这条 `05 EA 0C` 解释了为什么 `0x05` 占了全部指令的 25%：**每句台词都要调一次显示子程序**。
显示子程序里就是那些高频的中频 opcode（`0x79` `0x81` `0x85` `0x86` `0x87` `0x49` `0x31`），
它们一次文本执行一次，所以执行次数全都卡在 3130 上下。

这也给下一步指了路：**想还原画面，就去啃 `0x0CEA` 这个子程序**——它一定是「画文本框 + 排版 +
等按键」的那段代码。
