# 标题菜单、读档流程、原生菜单

> 这一篇记的是「玩家点一个按钮之后引擎到底做了什么」，包括标题四块木牌、
> `0xE5` 模态对话框、`LOAD.ISF` 的章节表，以及原版右键菜单里那些**不走脚本**的项。

## 1. 标题四块木牌

`TITLE.ISF` 第 98 条是 `0x07 vars[7]`，四个分支对应四块木牌（从左到右）：

| 木牌 | 槽号 | 分支 | 实际动作 |
|---|---|---|---|
| ゲームを終わる | 0（x 498..525） | `#219` | 淡出 → 等 500ms → `0x55` 全屏黑 → `0x06` 脚本结束 |
| 物置 | 1（x 528..555） | `#182` | 淡出 → `0x02 BGMLOAD`（BGM 鉴赏）→ `0x02 TCG`（CG 鉴赏） |
| 続きから | 2（x 558..585） | `#164` | 淡出 → `0xE5 1`（读档对话框）→ 等输入 |
| 始めから | 3（x 588..615） | `#100` | 淡出 → `0x01 SNR00`（第一章） |

槽的矩形来自 `0x84`：`588..615 × 308..455` 之类，宽 28 高 148 —— 木牌是竖排的。
「ゲームを終わる」那条最后 `0x06` 时返回栈是空的，等于**顶层结束**，
引擎主循环跟着退出。所以那不是卡死，是正常的「退出游戏」。

## 2. `0xE5`：模态对话框

```
E5 <u8 mode>
  mode 0 = 存档
  mode 1 = 读档
  mode 2.. = 设置（DoModal 的参数是 mode-2，即属性页页号）
```

处理函数 `FUN_0043D170 → FUN_0043F9A0`，关键点：

1. **模态**。`DoModal` 返回之前不会调 `FUN_00434EB0`，脚本就停在 `0xE5` 这一条上。
   我们的实现走同一条阻塞通道：`Vm::block_requested` + `Vm::unblock()`。
2. 读档模式会先 `FindFirstFileA` 检查存档文件在不在，不在就弹 MessageBox 直接返回。
3. 对话框返回 **10** 之后：

```c
*(engine + 0x7e7) = 0;
FUN_00435b00(vm);                      // 重置 VM（返回栈/模块栈清零）
FUN_00434b50(vm, &DAT_0047f4e8);       // DAT_0047f4e8 = "LOAD" → 载入 LOAD.ISF
FUN_00434eb0(vm);                      // 从 LOAD.ISF 第一条开始
```

`DAT_0047f4e8` 的字节是 `4C 4F 41 44 00 00 00 00`，就是 `"LOAD"`（后面紧跟错误
提示串）。**不是** START.ISF —— 早期笔记在这里错过一次。

存档（mode 0）成功之后不会重进剧本，只有读档（返回码 10）才会。

## 3. `LOAD.ISF`：章节表

`LOAD.ISF` 只有 128 条指令，主体就是一张 28 项的 `var[0x63]` 分派表：

```
47 63 ==  0 → #87   01 SNR00
47 63 ==  1 → #88   01 SNR01
   ...
47 63 == 27 → #114  01 SNRM3
默认（不在 0..27）→ var[0x0D] = 1 → 0x29 → 返回
```

28 个章节按剧本顺序是：

```
SNR00 SNR01 SNR02 SNR03 SNR04 SNR05 SNR06 SNR07 SNR08 SNR09
SNR10 SNR11 SNRC1 SNRC2 SNRJ1 SNRJ2 SNRA1 SNRA2 SNRM1 SNRM2
SNRR1 SNRR2 SNRBE SNRC3 SNRR3 SNRJ3 SNRA3 SNRM3
```

每个章节剧本的第一条就是 `var[0x63] = 章节号`（`SNR00` 第 5 条 `44 6300 00…`，
`SNRBE` 第 5 条写 `0x16` = 22），所以：

- **存档格里存的是章节号 + 位数组 + 变量数组，没有「剧本跑到第几行」**；
- 读档 = 恢复变量 → `LOAD.ISF` 按 `var[0x63]` 跳回那一章 → 章节脚本靠变量自己续上。

这解释了为什么 `docs/06-save.md` 里那个「尾部 0x30 全是 0」的结论是对的：
PC 版本来就不存 PC。

## 4. 原版右键菜单（不走脚本）

全库扫描：`0xE5` 在 40 个剧本里只出现 **1 次**（`TITLE.ISF` 第 171 条，mode 1）。
也就是说**存档、设置都不是脚本触发的**，是原生右键菜单：

| 菜单项 | 证据（`KIZUNAR.EXE` 字符串，VA = 文件偏移 + 0x400000） |
|---|---|
| セーブ / ロード | `0x47edfc` 起的 `"   Save   "` / `"   Load   "`，属性页 `CMyPropertyPage4..8` |
| 既読メッセージスキップ(&F) | `0x47ee..` |
| タイトルに戻る | `0x47f..` `"タイトルに戻ります。よろしいですか？"` + `"TITLE"` |
| 終了 | `0x47f654` `"ゲームを終了します。よろしいですか？"` |

所以 iOS 侧必须自己提供这几个入口（没有右键）：`App.swift` 的 ☰ 菜单里放
存档 / 读档 / 回标题 / 退出，分别对应 `kzn_save_open` / `kzn_title` / 系统退出。

「回标题」= `Engine::goto_title()` = 干净切换载入 `TITLE.ISF`（不是 START，
不走 logo）。

## 5. 设置

原版是 MFC 属性页 `CMyPropertyPage4..8`（`プロパティシート`），存在**注册表**里
（字符串里有 `SOFTWARE\\`、`.SUF`、`Control Panel\\Desktop`、`Wallpaper` ——
最后两项是「把 CG 设成桌面壁纸」的功能）。`KIZUNAR.SUF` 只是启动信息 INI，不是设置。

iOS 上没法照抄 Win32 属性页，现在的做法是：只保留引擎侧真正有两个旋钮——
`kzn_set_volume`（混音器 master）和 `kzn_set_speed`（打字速度），
用 SwiftUI 表单 + `UserDefaults` 存。**布局和原版不同**，这是已知差异。

## 6. 还没做的

- `物置` 里 `BGMLOAD` / `TCG` 之后的二级菜单（CG / BGM / SE 切换）。
- `0xF3` 的 MPEG（`DOLOGO.MPG` 开机 logo、`FAM_OP.MPG` 片头）。iOS 的 AVFoundation
  不认 MPEG-1，要还原得在打包时转成 H.264。
- 「把 CG 设成壁纸」——Windows 专属，iOS 不做。
