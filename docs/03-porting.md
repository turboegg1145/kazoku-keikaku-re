## 2. 三条路线

### 路线 A：用 Rust 写一个"ISF 解释器"（推荐）

不去翻译脚本，而是**照着原引擎的行为，在 Rust 里实现一个虚拟机**，直接读原版 `ISF` 文件。

- 好处：脚本、分支、旗标全部沿用原版，不用人工翻译 62,298 条台词对应的逻辑
- 好处：汉化补丁可以直接丢掉，中文用自己的字幕表
- 代价：要把 93 种 opcode 的行为一个个摸清楚（现在 7 种）

> 这是 Galgame 移植的常规做法。类似 KiriKiri / NScripter 的第三方播放器都是这么干的。

### 路线 B：把脚本"翻译"成自定义格式

把 ISF 反编译成人类可读的脚本（类似 Ren'Py 的 .rpy），再用现成引擎跑。

- 好处：以后改剧情/做汉化极方便
- 代价：93 种 opcode 还是得全懂，而且反编译出错很难查
- 适合：先把文本导出来做翻译，不适合直接做播放器

### 路线 C：原引擎 + 转译层

用 Wine / box86 / UTM 在 iOS 上跑原来的 `KIZUNAR.EXE`。

- 结论：**不现实**。iOS 不允许 JIT，App Store 也不允许这种分发方式；越狱机另说。

## 3. iOS 上的 4 个具体的坑

### 坑 1：视频（MPEG-1）

AVFoundation **不支持** MPEG-1。必须自己带解码器：

- 用 `ffmpeg` 的 `mpeg1video` 解码器（LGPL，注意合规）
- 或者干脆把 `FAM_OP.MPG` 转成 H.264 预置进包里（最简单，但要多占空间）

### 坑 2：音频

- OGG 需要 `libvorbis` / `lewton`（纯 Rust，推荐）
- iOS 的 `AVAudioEngine` 只吃 PCM，解码完丢给它就行
- 注意：11,215 + 11,081 个语音文件，**不要一次性全解压**，要流式

### 坑 3：文字排版

原引擎用 GDI 的 `TextOut` + 位图字体，直接照搬会糊。iOS 上要：

- 用 `CoreText` 或 `fontdue`（Rust）自己排版
- 竖排/禁则/标点挤压这些日式排版规则要自己写（原引擎也没有，所以可以简化）
- 中文字体要自带（iOS 内置字体不含完整简中黑体）

### 坑 4：渲染与输入

- 渲染：`wgpu`（Metal 后端）或 `SDL2` 都行，2D 精灵引擎不需要 3D
- 原引擎是 640×480 的 GDI 绘制，缩放策略要定（整数倍 + 黑边最稳）
- 输入：原版是鼠标右键/滚轮，iOS 要改成点击/长按/滑动
