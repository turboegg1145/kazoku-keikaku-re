# 文件格式

本文只记录**已实测通过**的结论。没验证的会明确标成"推测/未解"。

---

## 1. 归档容器 SM2MPX10

所有大文件（`GGD` `ISF` `SE` `VOICE1` `VOICE2` `WMSC` `DATA` `GGD2`）都是同一种容器。

| 偏移 | 长度 | 内容 |
|---|---|---|
| 0x00 | 8 | 魔数 `SM2MPX10` |
| 0x08 | u32 | 条目数 |
| 0x0C | u32 | 目录区大小（本作未使用，目录固定从 0x20 开始） |
| 0x10 | 12 | 归档内部名（NUL 填充） |
| 0x1C | u32 | 常量 `0x20` |
| 0x20 | 20×N | 目录项 |

目录项：

| 偏移 | 长度 | 内容 |
|---|---|---|
| 0x00 | 12 | 文件名，cp932，NUL 填充（8.3 风格，如 `SNR00.ISF`） |
| 0x0C | u32 | 数据偏移（绝对） |
| 0x10 | u32 | 数据长度 |

实测 8 个归档全部解析成功，**0 个越界条目**：

| 归档 | 条目数 | 大小 |
|---|---|---|
| GGD | 842 | 338,847,472 |
| ISF | 41 | 5,903,312 |
| SE | 136 | 5,324,080 |
| VOICE1 | 11,215 | 217,815,376 |
| VOICE2 | 11,081 | 206,041,504 |
| WMSC | 27 | 63,941,920 |
| DATA | 26 | 1,757,072 |
| GGD2 | 137 | 15,031,344 |

> 注意：网上流传的格式说明里有"目录偏移由头部给出 / 目录项 24 字节"的版本，与本作不符。本作目录固定 `0x20` 起、每项 20 字节。

工具：`tools/sm2mpx.py`

## 2. ISF 脚本

41 个文件，是**编译后的字节码**，不是文本。要过两层解密。

### 2.1 第一层：SECRETFILTER100a 异或壳

- 先丢掉文件末尾 16 字节（长度/校验尾巴）。
- 密钥不是常量：从 `KIZUNAR.EXE` 里那张 2048 字节的 `UOB0...` 表实时算出来（本作位于**文件偏移 0x74218**）。
- 算法：
  - 密钥长度 = `str2hex(encode_hex(secret[0x500+i] - secret[0x100+i]))`（i=0,1）
  - 密钥字节 = `encode_hex(secret[0x510+i] - secret[0x110+i])`
  - 每 klen 字节换一次密钥：`key[i] = encode_hex(key[i] + secret[(index & 0x3F)*0x10 + i])`
  - 全程用一张 36 字符表 `G5FXIL094MPRKWCJ3OEBVA7HQ2SU8Y6TZ1ND` 做"数字→字母"编码

### 2.2 第二层：ikuar_decrypt

按 `data[4:6]` 的版本魔数，对 offset 8 之后的全部字节做变换：

| 魔数 | 变换 |
|---|---|
| `0x9795` | 每字节循环右移 2 位 |
| `0xD197` | 每字节按位取反 |
| `0xCE89` | 每字节异或 `data[6]` |

本作 41 个文件全部是 `0x9795`。

### 2.3 解密后的布局

```
u32 head_len
u32 version (0x9795)
(head_len-8)/4 个 u32 偏移表   ← 全部落在文件内、数值各异，确认是有效表
head_len 起：指令流
```

例：`SNR00.ISF` head_len = 13288，偏移表 3320 项；`TCG.ISF` head_len = 32，偏移表 6 项。

### 2.4 指令流编码

```
opcode(u8) + len(u8) [+ ext]
len < 0x80  → 头部 2 字节，payload = len-2
len == 0x80 → 头部 3 字节，第 3 字节是长度
len == 0x81 → 头部 3 字节，第 3 字节 + 0x100
len 含头部自身
```

用这个规则切分，**41 个文件全部恰好切到文件末尾，无一失败**。总计 551,127 条指令、93 种 opcode。

### 2.5 指令语义

解释器是 `FUN_00434ec0`，**163 个合法 opcode 的处理函数地址已全部拿到**，详见
**[ISF 虚拟机](04-isf-vm.md)**。那里有执行模型、操作数编码（bit31=间接 / bit30=随机 / bit29=符号）、
表达式求值、以及完整的 opcode → handler 对照表。这里只列最常用的：

| opcode | 名称 | 语义 | 占比 |
|---|---|---|---|
| `0x44` | ASSIGN | `vars[u16] = expr`，expr 是 `(运算符, 操作数)` 链 | 27.0% |
| `0x05` | CALL | 压返回地址，跳标签 `u16` | 25.5% |
| `0xF4` | SET_FLAG | `engine+0x7FD = payload != 0` | 22.9% |
| `0x2B` | TEXT | 台词（见 2.6）| 11.3% |
| `0xF0` | VOICE_ARCHIVE | 语音所在归档，如 `\x04VOICE2` | 4.1% |
| `0x78` | VOICE | 语音文件名，如 `ONK0001` | 4.0% |
| `0x06` | RET | 返回 | 0.6% |
| `0x07` | SWITCH | 按选择子跳标签 | 0.6% |
| `0x02` | 命令名 | `BGMLOAD` / `SELOAD` | 0.5% |
| `0x56` | IMAGE | 图像资源名，如 `EFEC01.GG2` | 0.3% |

前 6 个就覆盖 95%。`0x2B` 的细节见下一节。

### 2.6 文本编码（0x2B 详解）

```
00 03 ff <cp932 文本> 00 00 00        叙述
00 03 04 <u8 说话人> ff <cp932 文本>   对白
```

- `0x00 0x06` = 句中换行
- `0x00 0x00` = 文本结束
- 其余 `< 0x20` 的字节是控制码（如 `0x02` 清窗口），显示时应丢弃

实测：`SNR00.ISF` 3141 条文本，其中 3080 条带语音文件名，语音与文本一一对应。全作共 62,298 条。

工具：`tools/isf_crypto.py`、`tools/isf_text.py`

## 3. 图像 GGD / GG0 / GG2 —— 全部解开 ✅

扩展名（`.GGD` / `.GG0` / `.GG2`）**不可靠**，一律按魔数分派。整条加载链：

```
FUN_0040a7d0  资源加载入口
  └ FUN_0040a720  嗅探 4 字节魔数
      ├ 返回 2 → FUN_0040aee0  GGD  加载器 → FUN_0040b190 解码 → FUN_0040b530 转 stride
      └ 返回 0 → FUN_0040a8e0  已经是 DIB，直接 CreateDIBSection

FUN_0040b650  GG0/GG2 加载器
  ├ FUN_0040b8b0  解码分派（DAT_004891a0 = CPU 特性开关）
  │   ├ FUN_0040b8e0  标量参考实现   ← 操作码表从这里抄
  │   └ FUN_0040bc90  MMX/SSE 版本（语义相同）
  └ FUN_0040b7f0  32bpp 中间缓冲 → 表面（+ 独立 8 位 alpha 面）
```

| 族 | 魔数 | 宽 | 高 | 像素 | 载荷起点 | 解码器 |
|---|---|---|---|---|---|---|
| A `GGD` | `b9 aa b3 b3` | u16 @0x04 | u16 @0x06 | 3 B，BGR | **0x08** | `FUN_0040b190` |
| B `GG0`/`GG2` | `"GGA00000"` | u16 @0x08 | u16 @0x0A | 4 B，BGRA | **0x30** | `FUN_0040b8e0` |

归档里 842 个成员：**50 个族 A + 792 个族 B**，两个解码器都已完整实现于 `tools/ggd.py`，
`tools/ggd_batch.py` 可以 842/842 全部导出成 PNG。

### 3.1 族 A：GGD（24bpp）

解码器 **`FUN_0040b190`（0x40b190–0x40b396）**，签名
`undefined4 FUN_0040b190(char *dst, int *reader, int nbytes)`。操作码表从反编译结果
**抄下来的**，不是猜的。50 个 `.GGD` 成员全部**精确消耗到最后一个字节**并精确产出 `w*h` 像素。

**流是扁平的操作码表**，没有行偏移表、没有分块头、没有「上一个距离」状态。
解满 `w*h` 个像素就停。

| 操作码 | 参数 | 长度 | 语义 |
|---|---|---|---|
| `00` | `<k>` | 2 | 重复上一个像素 `k` 次 |
| `01` | `<k> <d8>` | 3 | 从距离 `d` 复制 `k` 个像素 |
| `02` | `<k> <d16>` | 4 | 从距离 `d` 复制 `k` 个像素（**16 位距离**）|
| `03` | `<d8>` | 2 | 从距离 `d` 复制 1 个像素 |
| `04` | `<d16>` | 3 | 从距离 `d` 复制 1 个像素（**16 位距离**）|
| `05`–`FF` | — | `1+3*(b-4)` | 原始像素段，长度 = `b-4` |

- 像素 3 字节，**BGR** 顺序。
- 距离以**像素**计：源偏移 `(pos - d) * 3`。距离**可以跨行**——这正是 `02`/`04`
  存在的理由：640 宽的图往回一行是 640 像素，一个字节装不下。
- `05`–`FF` 一条能装 1–251 个原始像素，所以 `0xFF` = 251 个原始像素。
- 距离为 0 或大于当前位置都算非法，没有特例。
- 加载器 `FUN_0040aee0` 分配 `align4(w*3) * h` 字节的中间缓冲，再由 `FUN_0040b530`
  按行拷进表面；**流本身没有行填充**。

**这解释了汉化补丁的「填充字节」**：`ggd_sc/*.ggd` 不是「每 251 像素插一个填充字节」，
而是**每 251 像素写一个 `0xFF` 原始段头**。`0xFF` = 251+4，`0x8E` = 138+4（640 宽一行的
最后一段），`0x64` = 96+4（96 宽整行一段）。之前两天的「行步长 = (size-8)/h」只是这个结构的副作用。

**校验结果**（30 个 `ggd_sc` 补丁 vs 归档内压缩图，逐字节）：

| 图 | 尺寸 | 流消耗 | 像素差异 |
|---|---|---|---|
| CG2_BAO | 640×480 | 709622/709622 | 3576 px (1.2%)，首差 r10 c221 |
| CG2_BCH | 640×480 | 746911/746911 | 3727 px |
| EYE01 | 640×480 | 623246/623246 | 8754 px |
| MODORU | 96×96 | 20264/20264 | 4127 px，但**全是 ±1**（抖动） |

差异集中在**补丁重绘过的文字区域**，其余像素逐字节相同——补丁图是重新渲染/重新量化的，
不能当逐字节基准，只能当「结构 + 近似」基准。判断解码是否正确的硬标准是
**流是否精确消耗完 + 像素数是否精确**。

**未压缩补丁的写法**（`tools/ggd.py:encode_raw` 会生成同样结构）：每行按 251 像素切段，
每段一个 `n+4` 头字节后跟 `n` 个原始像素。

### 3.2 族 B：GG0 / GG2（32bpp BGRA）

加载器 **`FUN_0040b650`**，解码器 **`FUN_0040b8e0`**（标量参考实现；`FUN_0040bc90` 是等价的 MMX 版）。

**头部（48 字节 = 0x30）**：

| 偏移 | 类型 | 含义 |
|---|---|---|
| 0x00 | 8 B | 魔数 `"GGA00000"` |
| 0x08 | u16 | 宽 |
| 0x0A | u16 | 高 |
| 0x0C | u32 | flags |
| 0x10 | u32 | 载荷偏移，恒为 `0x30` |
| 0x14 | u32 | 载荷长度（= 成员大小 − 0x30）|
| 0x18 | u32 | 调色板偏移 |
| 0x1C | u32 | 调色板字节数 |
| 0x20 | u32 | 未知（加载器把它拆成两个 u16 存进对象 +0x1810/+0x1814）|
| 0x24–0x2F | — | 全 0 |
| 0x30 | — | 载荷 |

`flags` 只有两个取值：

| flags | 个数 | byte@0x0F | 含义 |
|---|---|---|---|
| `0x10200000` | 408 | `0x10` | bit0=0 → **没有 alpha 面**，第 4 字节被丢弃 |
| `0x11200000` | 384 | `0x11` | bit0=1 → **有独立 8 位 alpha 面** |

- `FUN_0040b650` 用 `(*(u8*)(hdr+0x0F) & 1)` 决定 `FUN_0040b7f0` 的最后一个参数；
  该参数为真时 `FUN_0040b7f0` 先把 BGR 写进彩色面、再把第 4 字节写进 `surface+0x24`
  指向的**独立 8 位 alpha 面**（不是 32bpp DIB）。
- `*(u8*)(hdr+0x0F) & 0x20` 是**调色板标志**：条目数 = `u32@0x1C / 12`（上限 0x200），
  数据在 `hdr + u32@0x18`，每项 12 字节（3 个 dword = RGB）。本作 792 个文件**一个都没用到**。
- 解码目标缓冲是 `w*h*4` 字节的线性缓冲（`GlobalAlloc(0, h*w*4)`）。

**操作码表**（`d` = 距离，单位**像素**；`k` = 像素个数）：

| 操作码 | 参数 | 长度 | 语义 |
|---|---|---|---|
| `00` | `<k8>` | 2 | 重复上一个像素 `k` 次 |
| `01` | `<k16>` | 3 | 重复上一个像素 `k` 次（16 位计数）|
| `02` | `<d8>` | 2 | 从距离 `d` 复制 1 个像素 |
| `03` | `<d16>` | 3 | 从距离 `d` 复制 1 个像素 |
| `04` | `<d8> <k8>` | 3 | 从距离 `d` 复制 `k` 个像素 |
| `05` | `<d8> <k16>` | 4 | 从距离 `d` 复制 `k` 个像素 |
| `06` | `<d16> <k8>` | 4 | 从距离 `d` 复制 `k` 个像素 |
| `07` | `<d16> <k16>` | 5 | 从距离 `d` 复制 `k` 个像素 |
| `08` | — | 1 | 复制上一个像素 |
| `09` | — | 1 | 从距离 `w` 复制（正上方那个像素）|
| `0A` | — | 1 | 从距离 `w+1` 复制 |
| `0B` | — | 1 | 从距离 `w-1` 复制 |
| `0C`–`FF` | — | `1+4*(b-0x0B)` | 原始像素段，长度 = `b-0x0B` |

- 像素 4 字节，**B,G,R,A** 顺序。
- 复制是**一个像素一个像素往前推**的，所以重叠复制会自我复制（和 C 循环一致），
  不能当成 `memmove`。
- `09`/`0A`/`0B` 是「上一行」专用操作码，这也证明距离单位是像素、行距就是 `w`。
- `0C` = 1 个原始像素，`FF` = 244 个原始像素。
- **解码器一直跑到载荷耗尽，从不检查 `w*h`**——像素数由流自己决定。所以实现时不要
  「解满就停」，要按 `p < len` 循环。

### 3.3 校验

| 族 | 成员 | 流精确耗尽 | 像素精确 = `w*h` |
|---|---|---|---|
| A `GGD` | 50 | 50 | 50 |
| B `GG0`/`GG2` | 792 | 792 | 791 |
| **合计** | **842** | **842** | **841** |

唯一的例外是 `TITLE.GG0`（640×480）：载荷 592,319 字节全部解析完，只产出 307,199 像素，
比 `w*h` 少 1 个。`tools/ggd.py` 用重复最后一个像素补齐（原版这里是未初始化内存）。

解码质量的旁证：`BAD_1.GG0`（640×480 照片）行内相邻像素平均差 11、行尾→行首平均差 18，
没有错行；`EFEC04.GG2` 的 alpha 恒为 `0x80`（半透明特效层）；`KA_M.GG2` 的 alpha 有 138 个
不同取值（窗口边缘的渐变）。

### 3.4 已排除的可能

见 `notes/negative-results.md`（十余条被否证的假设 + EXE 定位弯路）。
## 4. 音频 / 视频

- `WMSC` 归档里是 Windows Media 相关资源，本作未见播放路径
