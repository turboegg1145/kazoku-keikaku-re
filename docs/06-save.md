# 06 · 存档格式（KIZUNAR.SAV）

全部结论来自 `KIZUNAR.EXE` 的存档代码，并且用仓库里那份真实存档做了**逐字节回环验证**：
`sav.build(sav.parse(d), ...) == d` 成立。

## 1. 文件容器

```
0x0000   u32 offset[30]      120 字节的块偏移表
         block 0 .. block 29
```

- 块 i 的范围是 `[offset[i], offset[i+1])`，`offset[30]` 不存在，用**文件长度**代替；
- `offset[i] == 0` 表示该块为空（长度 0）；
- 块 0..26 = **27 个存档格**（3 页 × 9 格）；
- 块 27、28 = 引擎保留块，存档时**原样搬运**，不解析；
- 块 29 = 全局「已读文本」位图：`u32 压缩长度` + RLE 数据；
- 整个文件永远是先读 120 字节表，再按表取块；写档时先写 `SAVE.TMP`，成功后 `DeleteFile` + `MoveFile`。

## 2. 存档格（块 0..26）

```
+0x0000   SYSTEMTIME      16 字节：年/月/星期/日/时/分/秒/毫秒（8 × u16）
+0x0010   缩略图          0xE128 字节
+0xE138   标题            0xA0 字节，cp932，\0 补齐
+0xE1D8   扩展段描述      5 × (u16, u16)，引擎一律写 0
+0xE1EC   位数组          129 字节（1025 位）
+0xE26D   变量数组        542 × u32 = 2168 字节
+0xEAE5   尾部            0x30 字节 0
```

单格固定 **60,181 字节**（0xEB15）。27 格全满时文件约 1.55 MB。

### 2.1 SYSTEMTIME

Win32 `SYSTEMTIME`，8 个 u16。读档界面用它排序：
`key = 年*65536 + 月*256 + 日`，`次键 = 时*65536 + 分*256 + 秒`，取最大者即「最新存档」。

### 2.2 缩略图

不是 PNG，是 **40 字节 BITMAPINFOHEADER + 160×120×24bpp 像素**（57600 字节）：

```
biSize=40, biWidth=160, biHeight=-120 (top-down), biPlanes=1, biBitCount=24,
biCompression=0, 其余全 0
```

像素顺序 BGR，行优先、自上而下，无行对齐填充（160×3 = 480，本来就是 4 的倍数）。

### 2.3 位数组 / 变量数组

大小不是写在文件里的，而是脚本在启动时用三条指令**声明**的，所以是确定的：

| 指令 | 语义 | START.ISF 的操作数 | 结果 |
|---|---|---|---|
| `0x30 <u16 n>` | 位数组尺寸 = n+1 | `0x0400` | 1025 位 → 129 字节 |
| `0x40 <u16 n>` | 变量数组尺寸 = n+1 | `0x021D` | 542 个 → 2168 字节 |
| `0xA5 <u32 n>` | 已读文本位图 = n+1 | `0x7530` | 30001 位 |

三条都走同一个 `resize(n+1)`，失败就弹错误框并把 `vm->error` 置 1。

位数组就是 `0x31`（置/清/翻）与 `0x33`/`0x3B`（测试）操作的那一块；变量数组就是 `0x44` 的 `var[]`。

## 3. 位图 RLE

块 29（以及部分引擎内部数据）用的是一套**按位游程**编码，和 GGD 图像那套是同一个家族：

```
b0 的 bit7      = 这一段游程的位值（0 或 1）
b0 的 bit6..5   = 后续字节数 0/1/2/3（总长 1/2/3/4 字节）
b0 的 bit4..0   = 游程长度的高 5 位
后续字节        = 游程长度的低位，大端
```

位在字节里是 **LSB 优先**（`1 << (i & 7)`）。

编码器一直写到覆盖满 `ceil(nbits/8)` 字节为止，所以最后一段可能「超出」nbits，
这就是为什么 30001 位被编码成 30008 位：`40 75 38` = 30008 个 0。

## 4. 真实存档解剖

仓库里那份 `KIZUNAR.SAV`（2319 字节，玩家 2026-09-19 玩过）:

```
offset[0..26] = 0        27 个格子全空
offset[27] = 0x78        块 27，72 字节
offset[28] = 0xC0        块 28，2120 字节
offset[29] = 0x908       块 29，7 字节 = u32(3) + "40 75 38"
```

块 29 解出来是 30001 位全 0 —— 一局都没读过的「已读文本」位图，和「没有存档」完全吻合。

块 27（72 字节）= `{u32 512, u32 4}` + 64 字节全 0；
块 28（2120 字节）= `{u32 528, u32 20021227}` + 528 个 u32，其中 200 个是 `0xFFFFFFFF`、7 个是 1。

### 4.1 块 27/28 = 全局数组的落盘副本（`0x49` / `0x4A`）

`0x49`（`FUN_00439000` → `FUN_00434770`）以读写方式打开存档，从块表取第 `27 + which` 项的偏移，
`SetFilePointer` 到那里，然后：

- `which = 0`：`FUN_00423F10` 把全局位数组 `bits[start .. start+count]` **逐字节打包**写进去；
- `which = 1`：`FUN_00424CA0` 把 `vars[start .. start+count]` 以裸 i32 写进去。

`0x4A`（`FUN_00439060`）方向相反：`FUN_004241D0` / `FUN_00424D70` 从同一位置读回来。

指令格式是 `<start> <count> <x> <u8 which>`：前三个是 4 字节操作数，第四个是裸 u8。
第三个操作数 `x` 引擎**读了就丢**（老脚本残留），实际没用。

#### 块头 4 字节

**块 27/28 的**头 4 字节是容量**，数据从 `+4` 开始。三条独立证据：

1. `FUN_00423F10` / `FUN_00424CA0` 一进门就先 `read(4)`，拿这个值去夹 `start`/`count`，然后才写数据；
2. `0x48`（`FUN_00438A90`）在读已有存档时，就是 `seek(offset[27])` + `read(4)` 当作位数组容量；
3. `START.ISF` 第 4 条指令是 `0x48 00 02 10 02`（512 位 / 528 个），而真实存档块 27 的头 = **512**、
   块 28 的头 = **528**。按 `0x48` 的写法算长度：512 → `4+68` = **72 字节**（实测 72）；
   528 → `4+2116` = **2120 字节**（实测 2120）。

所以 `start` 是**变量/位下标**，从头部之后算起，和内存里的数组下标一一对应。

#### 容量从哪来（`0x48` 与 VM 构造）

引擎 VM 构造时（`0x433F10` 附近）就会调 `FUN_00434350` / `FUN_00434470`：
打开 `KIZUNAR.SAV`、读 28/29 个 u32 的块表（故意多读一个覆盖到栈上的 `offset[27]`/`offset[28]`），
确认两块偏移非 0 且不越界后，`seek` 到块首读 4 字节，分别写进 `+0x7D8` / `+0x7DC`。

`0x48 <u16 位容量> <u16 变量容量>`（`FUN_00438A90`）只做兜底：

```
if (+0x7D8 < 1 && +0x7DC < 1) {          // 文件里没有块 27/28（新装游戏）
    读块表 → 补齐空块偏移 → 块 0..26 原样复制
    块 27 = u32(位容量) + 全 0（长度 4 + ceil((((n+7)>>3)+4)/4)*4）
    块 28 = u32(变量容量) + 全 0（长度 4 + n*4 + 4）
    块 29 原样复制
    写 SAVE.TMP → DeleteFileA(正式文件) → MoveFileA(SAVE.TMP → 正式文件)
    +0x7D8 / +0x7DC = 脚本声明的容量
}
```

也就是说：**容量优先信存档文件，其次才信脚本**。这也是为什么改了脚本的 `0x48` 操作数，
老存档里的数组尺寸不会跟着变。

拿真实存档对一遍：块 28 的 529 个数据 u32 = `{20021227, 5, 0×7, 1, …}`，
脚本用 `vars[25]`（=5）当基址去读 `vars[56..147]`，落在一整段 `0xFFFFFFFF`（未设置）里 ——
和「鉴赏解锁表」的猜测吻合；块 27 的 68 字节数据里 `{u32 4}` 是位 34 置位，也是真实数据。

这条链路一通，故事脚本里每句台词前后都会 `0x4A` 读一次、`0x49` 写回一次（`start=31 count=91`），
也就是**全局旗标是随玩随写进存档文件的**，不是退出时才写。移植版必须同样处理。

## 5. 对移植版的要求

1. 读写必须是同一套字节布局，包括 0xE1D8 那 20 个 0 和尾部 0x30 个 0；
2. 缩略图要真画：把当前画面缩到 160×120、24bpp、top-down 写进去；
3. 块 27/28 能被 `0x49`/`0x4A` 原位改写，其余字节原样保留；
4. 读档时数组尺寸按 1025 位 / 542 个来，和 PC 版一致；
5. 写档走「临时文件 + 替换」，避免写一半断电把存档写坏。
